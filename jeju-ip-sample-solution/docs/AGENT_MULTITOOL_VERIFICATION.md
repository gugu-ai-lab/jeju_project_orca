# OpenAI 다중 도구 검증 (2026-11-02)

## 범위와 실행 결과

원본 프로젝트의 `codex/starter-setup`에서 서버 코드와 테스트만 변경했다. 프론트엔드, Supabase, 다른 브랜치는 변경하지 않았다.

실제 운영 진입 함수 `api/agent.js`를 호출했다. 로컬 HTTP 서버·브라우저를 거친 새 검증은 아니다. 함수의 HTTP 상태/JSON 응답 계약과 실제 외부 HTTP 요청을 확인했다.

모델 `gpt-6-luna`에 아래 질문을 한 번 전달했다. 특정 도구 이름을 지정하지 않았으며 `tool_choice: auto`로 선택했다. 마지막 요청은 기존 비용 제한에 따라 `none`으로 최종 답변만 생성했다.

> 삼성혈을 방문하려고 해. 관련 역사문화 자료, 관광지의 실제 주소와 소개, 제주시의 앞으로 몇 시간 날씨를 각각 확인하고 출처와 함께 한국어로 간단히 안내해 줘. 자료가 없거나 정확히 일치하지 않으면 확인하지 못했다고 말해 줘.

| 순서 | 선택 도구 | 실제 결과 |
| --- | --- | --- |
| 1 | `search_culture` | 제주역사문화일반정보 1건: 온평리해안. 설명에 삼성혈·삼성신화·혼인지 관계가 명시됨. 삼성혈 자체 항목은 아님 |
| 2 | `search_tour_places` | 한국관광공사 제주 삼성혈 1건. 주소: 제주특별자치도 제주시 삼성로 22 (이도일동). 소개·좌표·상세 조회 성공 |
| 3 | `get_weather` | 기상청 제주시 예보 6건. 모델에 13~15시 3건 전달, 18℃·맑음·강수확률 0%. 3건으로 제한했음을 메타데이터에 표시 |

공공데이터 HTTP 요청 5회, OpenAI HTTP 요청 4회. 자동 재시도 없음. 최종 상태 `completed`, `answerOrigin: model`, 한국어 답변 생성 성공. 도구 순서·출처·결과 미리보기 JSON 전달 확인.

캐시 토큰은 입력 합계에 포함되며 별도로 더하지 않는다. 계정 잔액은 조회하지 않았다.

## 실제 답변에서 발견한 오류와 보완

실제 답변은 삼성혈 주소와 날씨를 안내했지만, 관련 역사문화 자료가 없다고 과도하게 단정했다. 실제로는 온평리해안 설명에 관련성이 명시되어 있었다. 또한 조회 시각을 UTC 04:36으로 표기하면서 시간대를 밝히지 않았다. 한국 시각은 13:36경이다.

이에 정확한 이름의 항목 부재와 관련 자료 부재를 구분하도록 시스템 지침을 보완했다. 서버가 `fetchedAtKst`를 직접 계산하여 모델과 프론트엔드에 제공한다. UTC 원본 `fetchedAt`도 유지한다.

보완 후 전체 모의 테스트와 빌드는 통과했다. 비용 절약을 위해 추가 유료 요청은 하지 않았으므로 **보완 후 실제 모델의 표현 개선은 아직 재검증하지 않았다**. 프롬프트만으로 모든 의미 해석 오류가 사라졌다고 보장하지 않는다.

## 모의 테스트 범위

- 다섯 도구 등록 및 자동 선택 설정: 신화, 역사문화 일반, 역사문화 위치, 날씨, TourAPI.
- 연속 다중 도구 실행 및 마지막 자연어 답변 반환.
- 빈 결과와 API 오류 구분, 실패한 도구도 출처 유지.
- 전부 빈 결과/오류인 경우 모델의 확인되지 않은 답변을 서버의 안전 안내로 대체.
- 일부 도구 오류 후 다른 도구 계속 실행.
- 호출 순서, 출처 URL, 결과 개수, 미리보기의 JSON 전달.
- 모델 4회/도구 3회/최근 대화 6개/출력 600토큰/결과 5,000자 제한.
- 합산 토큰·캐시 입력 집계와 중간 모델 실패 시 이미 소비한 토큰 보존.
- 한국 표준시 변환 및 표시용 결과 개수 일치.

이번 유료 검증에서는 신화·역사문화 위치 도구를 모델이 선택하지 않았다. 이 둘의 이번 확인은 모의 테스트이며, 과거 실호출 검증과 구분한다. 모든 도구를 한 질문에 강제 호출하지 않는다.

최종 전체 테스트 39개 통과, 빌드 성공. 기존 프론트엔드 린트 경고 4개와 500kB 초과 번들 경고는 남아 있다.

## 프론트엔드 연동 계약

기존 `answer`, `steps[].tool/args/status/count/source/preview/error`는 유지한다. 기존 Store와 ToolSteps가 답변·도구 배열을 받는 구조도 확인했다. 화면 파일은 수정하지 않았다.

추가 필드:

- `steps[].sequence`, `modelTurn`: 실행 순서와 모델 요청 회차.
- `outcome`: `success`, `partial`, `empty`, `error`. 기존 `status`의 성공은 HTTP 처리 성공을 뜻하므로 빈 결과도 성공일 수 있다.
- `sourceUrl`, `fetchedAtKst`, `displayedCount`, `resultTruncated`, `notice`.
- 최상위 `warnings`, `answerOrigin`, `usage`, `modelCalls`.
- 공급자 오류 응답의 `usageIncomplete: true`: 알 수 있는 사용량만 집계되었음을 뜻한다.

Gemini는 후속 화면 통합에서 빈 결과/부분 결과 안내, 출처 링크, 한국 시각, 토큰 표시를 선택적으로 반영할 수 있다. 기존 Store는 토큰 집계를 별도로 저장하지 않는다.

명시적 재검증 명령은 `node --use-system-ca scripts/test-agent-multitool-live.mjs`이다. **실행 시 유료 호출이 발생하므로 일반 테스트에 포함하지 않았다.**
